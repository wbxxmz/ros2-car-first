## 1. 无人机仿真插件的 cmd_timeout 机制

### 1.1 问题发现

文档原版 run() 里多处用了 `time.sleep(1.0)` 等悬停等待。但仿真插件配置了 `<cmd_timeout>0.5</cmd_timeout>`（见 `inspection_task1.world` L435），意味着 **0.5 秒内没收到新的 `/uav/cmd_vel` 指令，插件进入超时状态，行为不可控**，会出现无人机一蹦一蹦的现象。

### 1.2 解决方案：hover() 函数

写一个 `hover(seconds)` 函数，悬停期间以 **20Hz 持续发零速度指令**，保证 cmd 不断流：

```python
def hover(self, seconds: float) -> None:
    deadline = time.monotonic() + seconds
    zero = Twist()
    while rclpy.ok() and time.monotonic() < deadline:
        rclpy.spin_once(self, timeout_sec=0.0)
        self.uav_cmd_vel_pub.publish(zero)
        time.sleep(0.05)   # 20Hz
```

### 1.3 关键对比

| 方式 | 频率 | cmd 断流？ | 结果 |
|------|------|-----------|------|
| `time.sleep(1.0)` | 0 Hz（不发指令） | 是（>0.5s） | 超时 → 可能漂移/掉高度 |
| `self.hover(1.0)` | 20 Hz（每 50ms 发零速度） | 否 | 插件保持悬停 |

> **类比**：simple_move 插件像"喂饭机器人"，每 0.5 秒得喂一次指令（零速度也算喂了）。`time.sleep` 就是 1 秒不喂饭→超时；`hover` 是每 50ms 喂一次零速度→机器人知道你还在控制它，保持悬停。

## 3. Nav2 状态污染：为什么"只有刚开 Nav2 时正常"

### 3.1 现象

任务跑过一次（成功或失败）后，Ctrl+C 杀了任务节点，重新跑——Nav2 就导不到正确点位了。

### 3.2 原因

**Nav2 不是无状态的**。任务失败后，以下状态残留在 Nav2 进程里：

| 状态 | 刚开 Nav2 | 跑过一次后 |
|------|----------|-----------|
| 全局 costmap | 干净，只有静态地图 | 残留"幽灵障碍物"（小车撞过的位置） |
| 本地 costmap | 干净 | 残留障碍物痕迹 |
| AMCL 定位 | 初始位姿正确 | 小车撞墙漂太远→粒子滤波器发散→定位漂了 |
| BT Navigator 状态机 | IDLE | 可能卡在 ABORTED |
| 小车物理位置 | 起点 | 撞墙后停在奇怪位置 |

### 3.3 根本原因

Ctrl+C 只杀了**任务节点**（minimal_user_node），**Nav2 和仿真进程还活着**，状态没清零。

### 3.4 解决原则

**仿真、Nav2、任务节点是绑定的三位一体**——哪一个挂了或跑失败，三个都要一起重启。

**决策树**：

```
任务失败/终止
  ↓
看 Gazebo 里小车位置正常吗？
  ├─ 正常 → 只重启 Nav2 + 任务节点即可
  └─ 漂了/撞墙 → 三个全重启（Sim → Nav2 → 任务）
```

### 3.5 一键启动 vs 手动启动

污染根源在 Nav2/Sim 内部状态，跟用脚本还是手动无关。唯一差别：手动启动不会被 gnome-terminal 的孤儿进程坑（关窗口≠杀进程）。
